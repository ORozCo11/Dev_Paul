What to test, and how

This covers every ability across all three portals — Admin, Custodian, and Maintenance Personnel — organized by module in the same order they appear in the sidebar.

Each card has a Scenario (a realistic situation to set up) and a Workflow (the exact steps to run through it). Check a card off as you confirm it works; progress is saved in this browser.

Use the role chips or the search box on the left to narrow the list while you're focused on one portal.

Authentication & Account

Log In

AdminCustodianMaintenance

Token-based sign-in. The account's role (or roles) determines which sidebar modules and dashboard appear after login.

ScenarioA tester needs to confirm all three portals look and behave correctly on first login.

Workflow
  1. Go to /login and sign in as an Admin account.
  2. Confirm the sidebar shows the full Admin module list and the Admin dashboard loads.
  3. Log out, repeat as a Custodian account, then as a Maintenance Personnel account.
  4. Confirm each portal only shows its own module set.

Remember Me

AdminCustodianMaintenance

Toggles whether the session token is kept in localStorage (survives closing the browser) or sessionStorage (cleared once the tab closes).

ScenarioA user logs in on a shared computer and wants to be sure they aren't left signed in.

Workflow
  1. Log in with Remember Me left unchecked.
  2. Close the browser tab entirely and reopen the app — confirm it's back at the login screen.
  3. Log in again with Remember Me checked, close and reopen the tab — confirm it's still signed in.

Log Out

AdminCustodianMaintenance

Clears the session from both storages and returns to the login page.

ScenarioEnd of a work session.

Workflow
  1. Open the account menu and click Logout.
  2. Confirm you land on /login.
  3. Try navigating back to a protected page directly — confirm it redirects to login instead of showing data.

Change Password

AdminCustodianMaintenance

Update your own password after verifying the current one, from the profile/account menu.

ScenarioA user wants to replace a temporary or weak password.

Workflow
  1. Open the profile/account settings panel.
  2. Enter the current password plus a new one and save.
  3. Log out and log back in using the new password to confirm it took effect.

Dashboard

The dashboard is role-scoped — every role sees vehicle totals, but the metrics, badges, and panels below them differ by which hat you're wearing.

Role-Scoped Metric Tiles

AdminCustodianMaintenance

Admin sees fleet-wide totals plus total maintenance expenses; Custodian sees their own reported-issue count; Maintenance Personnel sees records, upcoming/overdue maintenance, and vehicles needing attention.

ScenarioComparing what each role actually sees at a glance.

Workflow
  1. Log in as Admin, note every metric tile shown.
  2. Log in as Custodian, confirm "My Reported Issues" only counts that account's own reports.
  3. Log in as Maintenance Personnel, confirm "Vehicles Needing Attention" and maintenance-record metrics appear.

Readiness & Coverage Panel

Admin

Groups vehicles by type and shows ready vs. verified-ready vs. down counts, flagging a "no coverage" alarm when an entire type has zero ready units.

ScenarioThe barangay's only ambulance goes into the shop.

Workflow
  1. Open a ticket on the only vehicle of a given type and submit an inspection with "Needs Maintenance".
  2. Reload the dashboard.
  3. Confirm that vehicle type's readiness panel shows 0 ready and a no-coverage flag.

Single-Point-of-Failure Fragility

Admin

Flags any vehicle type currently down to one (or zero) ready units as a standing risk — before anything else even breaks.

ScenarioA type has two units; one is already under repair.

Workflow
  1. Send one of two same-type vehicles into an active ticket.
  2. Reload the dashboard.
  3. Confirm that type is flagged as fragile (single point of failure), and critical if the last one also goes down.

  2. Reload the dashboard.
  3. Confirm it appears in the overdue watch list.

  2. Reload the dashboard.

Recent Activity Feed

Issue Reports

Report a Vehicle Issue

AdminCustodianMaintenance

ScenarioA custodian notices a strange engine noise during a routine check.

Workflow

  3. Submit and confirm it appears in the list with status Pending.

The detail page shows the full-size photo, a distinct remarks callout, that vehicle's issue-history pie chart, the linked ticket (if one was opened from it), a report timeline, and the vehicle's last known map location.

ScenarioReviewing everything known about one reported issue in one place.

Workflow
  1. Open any issue report row.
  2. Confirm the photo, remarks callout, issue-history chart, linked ticket (if any), timeline, and location map all render correctly.

Edit an Issue Report

AdminCustodian

Correct a report's description, severity, or other details before it moves further along.

ScenarioThe initial severity was logged too low (or too high).

Workflow

  2. Save, then confirm the change reflects on both the list and detail view.

Delete an Issue Report

Removes a mistaken or duplicate report entirely.

  2. Confirm it no longer appears in the list.

Maintenance Tickets

The core workflow: a ticket is a Main Issue container. During inspection it's populated with one or more independent Sub-Issues, each running Open → Under Repair → For Inspection → For Confirmation → Done (or Deferred). The ticket itself only closes once every sub-issue has ended one way or another.

Create a Ticket

Admin

Opens a Main Issue on a vehicle and assigns it to a Custodian for physical inspection. Blocked on archived/decommissioned vehicles, and blocked if that same Main Issue is already open on that vehicle.

ScenarioA vehicle needs a formal maintenance ticket opened after an issue report or a routine finding.

Workflow
  1. Maintenance Tickets → Add. Pick vehicle, custodian, priority, and description.
  2. Submit and confirm the ticket shows status Open.
  3. Confirm the assigned custodian receives a notification.
  4. Try creating a second ticket with the same title on the same vehicle — confirm it's blocked with a message pointing at the existing ticket.

Submit Inspection

Custodian

Only the assigned custodian can inspect an Open ticket. "No Issues" effectively clears it; "Needs Maintenance" creates one sub-issue per real defect found and flips the vehicle to Under Maintenance.

ScenarioA custodian physically inspects the vehicle named on a newly assigned ticket.

Workflow
  1. Log in as the assigned custodian and open the ticket under Assigned Inspections.
  2. Submit inspection with result "Needs Maintenance" and two sub-issues.
  3. Confirm the ticket becomes Active and the vehicle's condition becomes Needs Repair.

Add a Sub-Issue Mid-Ticket

CustodianMaintenance

Appends a newly discovered defect while the ticket is Active. Only the assigned custodian, or a mechanic already working a sub-issue on this ticket, can do this — never Admin directly.

ScenarioMid-repair, a mechanic finds a second, unrelated problem.

Workflow
  1. As the assigned custodian or an assigned mechanic, open the Active ticket.
  2. Add a new sub-issue with a title and maintenance type.
  3. Confirm it appears in the sub-issue list as Open.

Assign a Mechanic (Work Order)

Admin

Dispatches one Open sub-issue to a Maintenance Personnel account along with a maintenance type. Only possible while the ticket is Active and that sub-issue is still Open.

ScenarioAn inspection just logged a sub-issue that needs a mechanic dispatched.

Workflow
  1. Open an Active ticket, pick an Open sub-issue.
  2. Assign a mechanic and a maintenance type.
  3. Confirm it becomes Under Repair and the mechanic receives a notification.

Reassign a Mechanic

Admin

Hands an in-progress (Under Repair) work order to a different mechanic, with a required reason — for when the original mechanic becomes unavailable.

ScenarioThe assigned mechanic calls in sick mid-repair.

Workflow
  1. Open a sub-issue that is Under Repair.
  2. Reassign it to a different mechanic with a reason.
  3. Confirm both the new and previous mechanic receive notifications, and the sub-issue stays Under Repair.

Log Repairs

Maintenance

Only the assigned mechanic can log what was actually done — logs, parts used, cost, dates, and an optional photo/receipt — which moves the sub-issue to For Inspection and notifies the custodian.

ScenarioA mechanic finishes physical work on an assigned sub-issue.

Workflow
  1. Log in as the assigned mechanic, open the work order under My Work Orders.
  2. Fill in repair logs, parts used, cost, and dates; attach a photo if relevant.
  3. Submit and confirm the status becomes For Inspection.

Verify Repair — Functional Test

Custodian

An independent UAT gate: the custodian runs a functional checklist and must attest they personally operated and tested the vehicle. A failed checklist item blocks approval outright — a failed test can never be Approved.

ScenarioA mechanic logged a repair; it needs independent proof it actually works.

Workflow
  1. As the assigned custodian, open the sub-issue that's For Inspection.
  2. Run the checklist with one item marked failed, try to Approve — confirm it's blocked.
  3. Mark everything passed, check the attestation box, Approve.
  4. Confirm the sub-issue moves to For Confirmation.

Reject a Repair

Custodian

The same verification screen — choosing Rejected instead sends the sub-issue straight back to Under Repair for the mechanic to redo.

ScenarioThe repair didn't actually fix the problem.

Workflow
  1. Verify a For Inspection sub-issue with verdict Rejected and notes explaining why.
  2. Confirm it returns to Under Repair and the mechanic is notified.

Confirm a Sub-Issue

Admin

The final Tier-2 sign-off. Confirmed marks the sub-issue Done and writes a permanent Maintenance Record with its cost/parts/dates; Reopened sends it back to Under Repair instead.

ScenarioA custodian has already approved the repair; Admin gives final sign-off.

Workflow
  1. Open a sub-issue that's For Confirmation.
  2. Confirm it Done.
  3. Check Maintenance Records for a new entry, and confirm the ticket's progress count increased.

Defer a Sub-Issue

Admin

Records a decision not to fix an item right now (e.g. a backordered part), with a mandatory reason. It becomes a terminal Deferred state, and a breadcrumb Issue Report is opened or resurfaced so the defect is never silently forgotten.

ScenarioA needed part won't arrive for weeks, but the rest of the ticket shouldn't be held up.

Workflow
  1. On an Active ticket, defer an unfinished sub-issue with a reason.
  2. Confirm it shows Deferred.
  3. Check Issue Reports and confirm a matching breadcrumb report now exists (or was resurfaced).

Close a Ticket — Clean Close

Admin

Available once every sub-issue is Done. Frees the vehicle back to Available/Good in one action.

ScenarioAll repairs on a ticket are confirmed and the vehicle is ready to go back into service.

Workflow
  1. Confirm every sub-issue on a ticket is Done.
  2. Close the ticket.
  3. Confirm the ticket becomes Closed and the vehicle returns to Available.

Close a Ticket — Decision-Close

Admin

Closing is still allowed with unfinished sub-issues, but requires a deferral reason (the leftovers auto-defer) and an explicit fit-for-service answer. Answering "not fit" keeps the vehicle under maintenance even after the ticket closes.

ScenarioA vehicle needs to be pulled from this ticket for budget or scheduling reasons, with real work still unfinished.

Workflow
  1. Close a ticket while a sub-issue is still Under Repair.
  2. Provide a deferral reason and answer "not fit for service".
  3. Confirm the ticket closes, the unfinished sub-issue shows Deferred, and the vehicle stays Under Maintenance rather than returning to Available.

Cancel / Uncancel a Ticket

Admin

Cancel is available at any point before Closed, and resets any linked issue reports back to Pending. Uncancel restores the ticket to whichever phase it was in (Open or Active) if it turns out it's still needed.

ScenarioA ticket was opened by mistake, then turns out to be needed after all.

Workflow
  1. Cancel an Open ticket, confirm it shows Cancelled.
  2. Confirm the vehicle frees up (if no other tickets are open on it).
  3. Uncancel it, confirm it returns to its prior phase.

Delete a Ticket

Admin

Fully discards a ticket. If it already had at least one Done sub-issue, it's archived as "Deleted" (recoverable) instead of vanishing outright. A Closed ticket can never be deleted.

ScenarioAn Admin accidentally deletes a ticket that had real progress on it.

Workflow
  1. Delete a ticket that has no completed sub-issues — confirm it's simply gone.
  2. Delete a different ticket that has at least one Done sub-issue — confirm it now appears in Ticket Archives tagged Deleted.
  3. Try deleting a Closed ticket — confirm it's blocked.

Ticket Archives

Browse Ticket Archives

Admin

A permanent log of every Closed or Deleted ticket, searchable and filterable by vehicle.

ScenarioLooking up a vehicle's full maintenance-ticket history.

Workflow
  1. Open Ticket Archives.
  2. Search by plate number, confirm matching archived tickets appear.

View a Closed Ticket

Admin

A closed ticket is permanently read-only, but its full history should still be reviewable through a View button.

ScenarioSomeone needs to double-check what was done on a ticket closed months ago.

Workflow
  1. Click View on a Closed archive row.
  2. Confirm the full ticket (sub-issues, verdicts, notes) opens without offering any edit actions.

Reopen a Deleted Ticket

Admin

Only archive entries tagged Deleted (never Closed) can be recovered — restores the ticket and every sub-issue exactly as it stood, blocked if a duplicate Main Issue already exists on that vehicle.

ScenarioA ticket deleted earlier turns out to still matter.

Workflow
  1. Find a Deleted archive entry and click Reopen.
  2. Confirm a new ticket is created with the same sub-issues and progress restored.

Decommission a Vehicle

Admin

A permanent end-of-life write-off with a required reason. Blocked while any ticket on that vehicle is still open.

ScenarioA vehicle is beyond economical repair.

Workflow

  3. Confirm its status becomes Decommissioned.

Readiness Check

AdminCustodian

A pass/fail checklist proving a vehicle will actually start and respond — not just that it has no open repair. Feeds the dashboard's "verified ready" vs. merely "available" distinction.

ScenarioConfirming an available vehicle is genuinely dispatch-ready.

Workflow
  1. Open a vehicle's profile and run a readiness check with one item marked failed.
  2. Confirm its state shows "not ready".
  3. Run it again with everything passed, confirm it shows "ready".

View Vehicle Reliability

Admin

ScenarioDeciding whether a vehicle is becoming unreliable.

  2. Confirm the reliability view accurately reflects that history.

Maintenance Schedule

Preventive maintenance planned ahead of time, separate from reactive ticket repairs.

Create a Maintenance Schedule

AdminMaintenance

Books a future preventive-maintenance date for a vehicle, with a service location (dropdown of hubs, or "Other" free text) and optional assigned personnel. Blocked if that vehicle already has a Scheduled entry the same day. Can optionally recur every N months.

ScenarioBooking a routine oil change three weeks out, recurring every 6 months.

Workflow
  1. Maintenance Schedule → Add. Confirm the date field defaults to tomorrow.
  2. Pick a hub from the Service Location dropdown (or choose "Other" and type a location).
  3. Set a recurrence interval, submit, confirm it shows Scheduled.
  4. Try adding a second schedule for the same vehicle on the same date — confirm it's blocked.

Edit a Maintenance Schedule

AdminMaintenance

Update date, location, or notes. The Status field on this form only ever offers Scheduled or Cancelled — "Completed" is deliberately unreachable here, to force going through the proper Mark Done flow instead.

ScenarioA booked service date needs to move.

Workflow
  1. Edit an existing schedule's date or location, save.
  2. Confirm the change sticks.
  3. Confirm the Status dropdown never offers "Completed" as an option.

Mark a Schedule Done

AdminMaintenance

One action that completes the schedule, writes a proof-of-work Maintenance Record, and — if the schedule recurs — automatically books the next occurrence at the configured interval.

ScenarioA recurring oil change was just performed on schedule.

Workflow
  1. Open a recurring Scheduled entry, click Mark Done.
  2. Fill in cost/notes and confirm.
  3. Confirm a new Maintenance Record was created, the schedule shows Completed, and a new Scheduled entry now exists at the correct future date.

Cancel a Maintenance Schedule

AdminMaintenance

Deleting a schedule cancels it rather than erasing it outright, keeping a record that it was once planned.

ScenarioA planned service is no longer needed.

Workflow
  1. Delete a Scheduled entry.
  2. Confirm it now shows Cancelled rather than disappearing from the list.

Maintenance Records

The unified ledger of completed and in-progress repair work, whether it originated from a ticket, a schedule, or a standalone entry.

Add a Maintenance Record

AdminMaintenance

Logs standalone repair work directly, outside the ticket flow. A pure mechanic account always logs it under their own name; Admin can assign it to someone else.

ScenarioA quick repair happens outside the formal ticket process.

Workflow
  1. As Maintenance Personnel, add a record for a vehicle.
  2. Confirm it's attributed to your own account and the vehicle flips to Under Maintenance / Needs Repair.

Verify a Maintenance Record

Custodian

The same Tier-1 verification concept as tickets — the Custodian marks a For Verification record Passed or Failed. Failed bounces it back to Under Repair.

ScenarioA standalone repair needs independent sign-off before it's considered done.

Workflow
  1. Verify a For Verification record as Failed, confirm it returns to Under Repair.
  2. Repeat with Passed, confirm it stays For Verification awaiting Admin confirmation.

Confirm a Maintenance Record

Admin

Final sign-off after a Passed verification. Confirmed marks it Completed and returns the vehicle to Available / Good; declining sends it back to Under Repair.

ScenarioA Custodian has already passed the repair; Admin gives final confirmation.

Workflow
  1. Confirm a Passed record.
  2. Confirm its status becomes Completed and the vehicle is Available again.
