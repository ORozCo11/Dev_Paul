# VMS QA Report, 21 November 2026

Environment: local (API 127.0.0.1:8001, SPA localhost:5173), branch `dev-paul` at `a366d2f`. Roles tested through the supported account switcher (impersonation) as Pahina Admin, Custodian and mechanics, plus another barangay (Hippodromo) for isolation. Fixtures were prefixed `QA-1121-` and have been removed; the number sequences were restored. No source code was changed. No real email was sent.

## Summary

About 160 checks were run: the Super Admin and public area (API only), about 130 role-workflow checks (API), and 108 browser page loads (3 roles × desktop, mobile and dark mode). The core process works as designed. Every attempt to step outside a role or a barangay was refused by the server. There were no JavaScript errors, no server 5xx errors, no horizontal overflow and no "undefined/NaN" text on the pages visited.

The concerns below are ranked by how much they matter.

## What held up (controls that worked)

- Authentication: all protected routes refuse no token (401); wrong login gives a generic message.
- Super Admin is limited to account administration (fleet, tickets, vehicles, impersonation list all 403).
- Roles: mechanic cannot create vehicles, conditions, readiness checks, schedules or tickets; Admin cannot record condition or readiness checks (Custodian duty); the Custodian cannot approve their own ticket or schedule; the Admin cannot verify; the mechanic cannot verify their own work; a mechanic who is not assigned cannot log repairs, return, or mark no repair.
- Barangay isolation: another barangay's Admin, Custodian and mechanic were refused (403 or 404) on reading, editing, archiving, approving and verifying; their lists show none of the Pahina data.
- Validation: blank vehicle, duplicate plate number, future and ancient model years, no sub-issues, bad priority, short reasons, negative cost, future repair dates, completion before start, "tested" confirmation, readiness confirmation, bad condition result were all refused.
- Lifecycle: propose → approve with mechanic → log repairs with test → submit → Custodian reject with a failed item → rework → resubmit → approve. The ticket closes, one record is written, the vehicle returns to Available/Good with readiness "unchecked" (it needs a Custodian check before it counts as Ready), as designed. Verify twice, delete a closed ticket and cancel a closed ticket are all refused.
- Branches: request corrections, decline (reason needed), undecline, cancel (notes needed), return to Admin and no repair needed (short notes refused). A second open ticket for the same vehicle is refused. Archive, decommission and mark-available are refused while a ticket is open. Cannibalization refuses a donor that is still in use (must be decommissioned).
- Schedules: approve needs the Admin of the same barangay; a duplicate schedule on the same day for one vehicle asks for confirmation (409); decline needs a reason.
- Browser: Admin, Custodian and mechanic pages at desktop, mobile (390 px) and dark mode loaded with no errors, no overflow, no blank pages, no "undefined/NaN/null" text.

## Not covered (partial)

- Account creation emails, resend credentials, temporary-password expiry (blocked: real SMTP).
- Login throttle (would lock the shared address), Super Admin self-deactivation (only Super Admin).
- Browser walk of the sub-pages under a folded Maintenance folder, file uploads and previews, export files (CSV/PDF), two people acting at the same moment, and the scheduler converting a due schedule (not forced, to avoid changing real data).
- External-shop send/return was only reached through the mechanic's endpoints after the "needs external reason" validation; the full external round trip should be walked once in the browser.

## Cleanup

All `QA-1121-` vehicles, tickets, work items, schedules, records, notices, history and activity rows were removed and the number sequences restored. The two real overdue schedules were left untouched.

## Update, 22 November 2026

Everything raised above has been fixed or settled, and a second, wider test pass was run (about 400 cases in `VMS-Test-Cases-2026-11-21.pdf`).

Fixed since the first report: past-dated and past-moved schedules, schedule approval without a mechanic (the Admin now picks one), ticket description length, error replies showing file paths (`APP_DEBUG=false`), local mail set to log, the Account Switcher showing in the Super Admin list, the public barangay list, the shared rate-limit counter (each limit now has its own), unknown report types and reversed report date ranges, and notices having no screen (a bell in the top bar now lists them).

One municipality: the database now holds only Cebu City and its 80 barangays (backup kept outside the project folder), the add-barangay form and the province and city filters are gone, and the Super Admin sees all 80 barangays with a "N of 80 have an Administrator" dashboard.

Settled without a change: the Super Admin barangay list is a fixed 80 rows (no paging needed); the users list is paged in the browser.

Still to do outside this project: set `APP_DEBUG=false` and a real mail setting on the deployed server, and make sure the scheduler runs there.
